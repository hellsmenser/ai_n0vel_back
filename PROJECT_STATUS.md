# Project Status — AI Novel (Diploma)

Дата аудита: **2026-10-19**

## Итог

Проект находится на стадии **работающего локального прототипа отдельных частей**, но не готов к выпуску. Этапы 0–4 Ren'Py-клиента реализованы локально: контракт сцены v1, сохраняемый snapshot, пошаговый cursor, save/load, rollback, History, `SceneProvider`, наблюдаемые ошибки и стабильная autosave-граница покрыты native-тестами. Полный запуск Ren'Py → MongoDB → Python-оркестратор на чистом окружении всё ещё не подтверждён; реальной интеграции с LLM нет.

Принятое направление: **AI Gateway реализуется на Python**, а не на Node.js/TypeScript.

## Фактический поток данных

1. `Novel/game/tasks.rpy` подключается напрямую к MongoDB и создаёт задачу со статусом `new`.
2. `orchestrator/core/task_manager.py` получает событие Change Stream.
3. Оркестратор проводит задачу через состояния:

   ```text
   new → ready_to_generate → generating → generated
       → ready_to_compile → done
   ```

4. `orchestrator/core/scene_generator.py` возвращает шаблонный JSON.
5. На этапе `ready_to_compile` оркестратор пишет `Novel/game/scenes/scene_<id>.json`.
6. Ren'Py получает задачу через `SceneProvider`, читает файл, выполняет действия через registry обработчиков, подтверждает `done → consumed` и только затем создаёт стабильную autosave-границу.

## Результаты проверок

### Пройдено

- `docker compose config --quiet` — конфигурация валидна.
- AST-разбор собственных Python-файлов оркестратора — без синтаксических ошибок.
- Изолированный smoke test — 1000 уникальных сцен с v1-валидацией сформированы успешно.
- Все пять сохранённых JSON-сцен корректно разбираются как JSON.
- Переменные `MONGO_URI` и `MONGO_DB_NAME` присутствуют; URI указывает на Compose host и replica set.
- Ошибка `bg room` исправлена заменой на объявленный `bg_tavern_interior`; Ren'Py 8.3.4 lint с `--error-code` завершается с кодом 0.
- Native testcase `default` воспроизводит автономную JSON-сцену через общий playback pipeline и завершается с кодом 0.
- Testcase подтверждает по одной записи для трёх уникальных реплик в `_history_list` и создаёт screenshot с фоном, обоими персонажами и финальным маркером.
- Пошаговый player проверен на progression, save/load, rollback 1/3/10, границе сцен, `return`, natural end, `goto`, handler error и hard checkpoint паузы.
- History использует один штатный `renpy.say` на реплику, callback-аннотации и доступный переход `RollbackToIdentifier`; save-slot metadata хранит только инертное описание state.
- Недоверенный текст экранирует Ren'Py interpolation/tags, а JSON `jump` ограничен явным production allowlist.
- History UI содержит три fixture-реплики; обычное прохождение, `return`, `jump`, граница сцен, skip и auto доходят до своих контрольных точек.
- `animate` с объектом `shake` и fade/dissolve больше не падают; неизвестное действие и отсутствующий ресурс отклоняются до handlers.
- Очередь после нормального `return` требует подтверждённый `done → consumed`, не удаляет Mongo-запись и повторяет ack без дублирования successor-задачи. Оркестратор публикует файл через temp + fsync + replace + повторную проверку.
- Save/load повторяет только текущую незавершённую реплику и хвост (`1/2/2`), не первую завершённую. Недоступная MongoDB теперь за несколько секунд приводит к структурированной ошибке `provider_offline` с действиями Retry/Main Menu, а не к 60-секундному зависанию.
- `SceneProvider` отделяет игровой цикл от источника сцены; provider runtime не попадает в save. Poll/refill ограничены бюджетом, retry acknowledgement не переигрывает сцену, а playback retry разрешён только для действий без частично выполненного пользовательского эффекта.
- Autosave выполняется блокирующе только после завершённой сцены и подтверждённого внешнего ack. Настоящая загрузка autosave проверяет восстановление `boundary`, а несовместимый `SceneSessionState` отклоняется fail-closed.
- Полная матрица 2026-10-19: JSON fixtures `37/37`, Ren'Py 8.3.4 lint `PASS`, native testcases `62/62`, `overall_passed=true`, свежих `traceback.txt`/`errors.txt` нет. Offline-cases прошли за 5,762 и 5,879 секунды при закрытом MongoDB port.

### Не подтверждено

- Сборка Docker-образов и запуск контейнеров: Docker daemon не работал во время аудита.
- Миграция старых `PlaybackState`: реальный `FileLoad` проверен, но несовместимые версии намеренно отклоняются fail-closed и отправляют игрока в главное меню.
- Вызов реальной LLM: интеграции нет.
- Сквозное восстановление worker после падения и реальный Compose/MongoDB lifecycle; локальные клиентские offline/invalid-scene состояния проверены fixtures и отключённым портом.

`docker compose config` также сообщает, что ключ верхнего уровня `version` устарел и игнорируется современным Compose.

## Основные риски

### Принято — система разделена на client и backend

Исходный рабочий каталог содержал три Git-репозитория. Публичная структура упрощена до двух:

- [ai_n0vel](https://github.com/hellsmenser/ai_n0vel) — Ren'Py-клиент;
- [ai_n0vel_back](https://github.com/hellsmenser/ai_n0vel_back) — Python-оркестратор, MongoDB Compose и общая документация.

Оба репозитория используют ветку `main`. `.env`, MongoDB volume, saves, тестовые artifacts, виртуальные окружения, кэши, логи и сгенерированные сцены исключены.

**Оставшееся ограничение:** для полного локального запуска нужны оба соседних clone. Compose получает путь к клиенту через `NOVEL_CLIENT_PATH`.

**Нужно:** при необходимости добавить release-архив или bootstrap-скрипт, клонирующий оба репозитория совместимых версий.

### Высокий — MongoDB открыта без прикладной границы безопасности

MongoDB публикует `27017:27017`, запускается с `--bind_ip_all` и без включённой аутентификации. Ren'Py подключается напрямую и содержит URI и имя базы в коде.

**Последствие:** при доступности порта из сети клиент может читать и изменять задачи без авторизации.

**Нужно:** до любого нелокального развёртывания закрыть внешний порт или ограничить bind address, включить аутентификацию и убрать прямой доступ Ren'Py к базе за API/локальный адаптер.

### Высокий — обработка задач не восстанавливается после сбоев

Оркестратор реагирует только на новые Change Stream events и не выполняет стартовый sweep. Захват задачи не атомарный. Задача может навсегда остаться в `generating` или другом промежуточном статусе после падения процесса. Нет lease, attempts, deadline или retry policy.

**Нужно:** добавить атомарный claim через `find_one_and_update`, поля `attempt`, `lease_until`, `worker_id`, обработку timeout и восстановление незавершённых задач при старте.

### Средний — контракт v1 реализован в двух средах

Ren'Py проверяет загружаемый JSON и реальные объявления изображений; Python-оркестратор использует dependency-free mirror тех же правил и whitelist ресурсов. Текущие boundary-тесты и native invariant подтверждают совпадение, однако при расширении формата два валидатора и JSON Schema можно рассинхронизировать.

**Нужно:** при каждом новом action/resource менять Schema, оба валидатора, registry и parity-тесты одной логической поставкой; в будущем генерировать часть валидаторов из одной схемы.

### Исправлено локально — ложный `done` после ошибки записи

`handle_ready_to_compile()` проверяет v1 и соответствие task id, пишет временный файл в целевом каталоге, выполняет `fsync`/`os.replace`, перечитывает результат и только затем ставит `done`. Ошибки получают структурированный статус `error`. Сквозная проверка на реальной MongoDB ещё не выполнена.

### Средний — синхронный PyMongo находится внутри asyncio-кода

`collection.watch()` и CRUD-вызовы блокируют event loop. `await asyncio.create_task(...)` фактически сохраняет последовательную обработку и не даёт полезного параллелизма.

**Нужно:** выбрать один подход: обычный синхронный worker либо асинхронный MongoDB driver/адаптер с ограниченной конкуренцией.

### Исправлено локально — ошибки Ren'Py получают наблюдаемую границу

`SceneProviderError` различает poll/prepare/playback/acknowledge, показывает безопасное сообщение и Retry/Main Menu. Обычные ошибки не смешиваются с Ren'Py control-flow exceptions; невалидные scene/session state отклоняются fail-closed.

**Ограничение:** Mongo polling всё ещё синхронный на interaction thread. Короткие timeouts и bounded work ограничивают паузу, но production-вариант должен вынести I/O в локальный адаптер, API или worker/event queue.

### Средний — документация описывает другую систему

Старые документы говорят о Redis, C# compiler, генерации `.rpy` и статусах `json_pending/json_ready/ready`. В коде этих компонентов и статусов нет.

**Нужно:** после решения по JSON-player и сервисным границам синхронизировать `docs/architecture.md`, `docs/deployment.md` и `docs/renpy_integration.md`.

## Решение по Python AI Gateway

Предлагаемая зона ответственности будущего компонента:

1. Атомарно получать задачу, подготовленную к генерации.
2. Собирать prompt из контекста игрока, предыдущей сцены и ограничений мира.
3. Вызывать выбранный LLM API через настраиваемый Python-адаптер.
4. Разбирать ответ и валидировать его по версионируемой JSON Schema.
5. Проверять допустимые actions, персонажей и ссылки на ресурсы.
6. Записывать `result`, метаданные модели и статус `generated` либо структурированную ошибку.
7. Поддерживать timeout, ограниченные retries и идемпотентность.

До реализации остаются открытыми решения:

- какой LLM provider используется первым;
- AI Gateway будет отдельным контейнером или Python-модулем оркестратора;
- сохраняется ли прямой доступ Ren'Py к MongoDB;
- как синхронно версионировать совместимые релизы client и backend.

## Рекомендуемый порядок стабилизации

Baseline-коммиты и безопасные ignore-правила созданы; client и backend опубликованы в ветках `main`. Этапы 0–4 клиента реализованы; следующий клиентский шаг — Этап 5, единый кастомный GUI. Серверный параллельный шаг — recovery/lease и реальный end-to-end smoke.

2. Добавить recovery/lease/retry в обработку задач.
3. Поднять Compose и выполнить воспроизводимый end-to-end smoke test.
4. Реализовать Python AI Gateway поверх проверенного контракта.
5. Добавить music только вместе с handler и реальными ресурсами.
6. Обновить вторичные документы и добавить CI.

## Критерии следующей контрольной точки

Следующий этап можно считать завершённым, когда:

- чистый clone не содержит секретов и локальной базы;
- `docker compose up --build` поднимает healthy MongoDB и worker;
- тестовая задача проходит полный жизненный цикл без ручного вмешательства;
- сцена валидируется до `done` и полностью воспроизводится в Ren'Py;
- после принудительного перезапуска worker зависшая задача восстанавливается;
- Python AI Gateway генерирует хотя бы одну сцену через выбранный LLM provider;
- автоматические проверки подтверждают контракт и переходы состояний.
