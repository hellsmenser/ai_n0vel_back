Этот файл сохраняет решения, альтернативы и наблюдения, из которых позже можно собрать разделы пояснительной записки для курсовой и диплома. Запись считается фактом только там, где указана проверка; планы и гипотезы помечены отдельно.

## Шаблон записи

- **Решение** — что выбрано и в каком статусе находится.
- **Альтернативы** — какие варианты рассматривались.

## D-001. JSON остаётся исполняемым форматом сцены

**Дата:** 2026-10-16
**Статус:** принято, текущая архитектура

**Контекст.** Генератор создаёт динамические сцены. Старые документы упоминали отдельный C# compiler и генерацию `.rpy`, однако текущий клиент уже читает JSON и передаёт действия зарегистрированным Ren'Py handlers.

**Решение.** Не генерировать Ren'Py script на каждую сцену. Хранить сцену как JSON snapshot и исполнять её внутри клиента.

**Альтернативы.** Генерировать `.rpy`; вернуть отдельный compiler; передавать готовый Ren'Py-код от LLM.

**Компромиссы.** JSON проще валидировать, версионировать и безопасно ограничивать. При этом динамические действия не получают автоматически семантику Ren'Py script: текущий вызов, выполняющий всю сцену внутри одного Python statement, плохо согласуется с save/load и rollback.

**Проверка.** Stage 0 fixtures проходят через тот же `play_json_scene_file()` и registry handlers, что и production JSON-player.

**Последствия.** Нужны строгая JSON Schema, версия контракта, проверка ресурсов и пошаговый проигрыватель.

## D-002. AI Gateway реализуется на Python

**Дата:** 2026-10-16
**Статус:** принято, ещё не реализовано

**Контекст.** В проекте уже есть Python-оркестратор и Python-зависимости; ранее обсуждался Node.js/TypeScript gateway.

**Решение.** Реализовать AI Gateway на Python.

**Альтернативы.** Отдельный Node.js/TypeScript сервис; встраивание вызова LLM в Ren'Py; сохранение демонстрационного генератора как production-компонента.

**Компромиссы.** Один язык для orchestration, schema validation и LLM SDK уменьшает эксплуатационную сложность. Отдельная сервисная граница всё равно нужна, чтобы не помещать сеть, секреты и retry-логику в игровой клиент.

**Проверка.** Пока подтверждено только архитектурное направление; реального LLM-вызова нет.

**Последствия.** До реализации gateway требуется зафиксировать контракт сцены, атомарный claim задачи и структурированные ошибки.

## D-003. Состояние проигрывания должно быть явным и сохраняемым

**Дата:** 2026-10-16
**Статус:** реализовано локально в Этапах 1–3

**Контекст.** Ren'Py сохраняет позицию на границе script statements. Текущий JSON-player исполняет цикл по всей сцене внутри одного Python statement.

**Решение.** Ввести `PlaybackState` с snapshot сцены, `scene_id`, `schema_version`, `content_hash`, `step_index`, фазой и структурированной ошибкой. Выполнять одно JSON-действие за итерацию Ren'Py label loop и увеличивать курсор только после успеха.

**Альтернативы.** Оставить единый Python-вызов; генерировать `.rpy`; хранить только индекс без snapshot содержимого.

**Компромиссы.** Явное состояние добавляет код и миграции save-формата, зато делает поведение наблюдаемым и позволяет отделить rollbackable сюжет от внешней очереди и MongoDB.

**Проверка.** Stage 0 воспроизвёл проблему: после load probe-счётчики были `2/2/2`, после rollback — `2/1/1`. После пошагового цикла save/load даёт `1/2/2`: завершённая первая реплика не повторяется, текущая вторая закономерно исполняется заново после восстановления statement.

**Последствия.** Следующий этап начинается с версии контракта и `PlaybackState`, а не с косметического исправления экранов save/history.

## D-004. Сначала characterization baseline, затем исправления

**Дата:** 2026-10-17
**Статус:** реализовано

**Контекст.** Проект давно не запускался, а часть воспоминаний о save/load, history и rollback могла быть неточной. Исправления без baseline могли изменить или скрыть несколько независимых дефектов.

**Решение.** Этап 0 не исправляет production-логику. Он фиксирует текущее поведение отдельными immutable fixtures и native testcases; известный дефект считается совпавшим с baseline только по точному наблюдаемому признаку.

**Альтернативы.** Сразу переписать player; ограничиться ручным запуском; проверять только happy path.

**Компромиссы.** Некоторые сценарии имеют `PASS`, хотя production-поведение ошибочно. Поэтому runner и документация явно различают «baseline совпал» и «функция исправна».

**Проверка.** Полная матрица: 13/13 JSON fixtures, lint `PASS`, 15/15 сценариев, `overall_passed=true`. Отдельно зафиксированы `ATLTransform`, `MultipleTransition`, неизвестный `music`, отсутствующий фон, save/load, rollback и start без MongoDB.

**Последствия.** При каждом исправлении соответствующее ожидание меняется с воспроизведения дефекта на правильный результат; regression case не удаляется.

## D-005. Тесты закреплены на Ren'Py 8.3.4 и изолированы по процессам

**Дата:** 2026-10-17
**Статус:** реализовано локально

**Контекст.** Поведение native testcase, save-файлов, history и исключений зависит от версии движка и process-global состояния.

**Решение.** Использовать SDK `F:\renpy\renpy-8.3.4-sdk`. Каждый сценарий запускается в отдельном процессе и получает отдельный `--savedir` внутри игнорируемого `test-artifacts/`, изолированный от пользовательских saves и других cases. Там же сохраняются diagnostics и screenshots.

**Альтернативы.** Один процесс для всей матрицы; пользовательский каталог saves; только lint; более новая непроверенная версия SDK.

**Компромиссы.** Полный прогон занимает несколько минут из-за отдельных процессов и реальных save/load interactions. На исходном baseline дополнительную минуту занимал намеренный offline-timeout; после Этапа 4 он заменён проверкой наблюдаемого `provider_offline` с лимитом 8 секунд. Изоляция исключает зависимость от порядка, но не заменяет отдельные regression-проверки cleanup внутри одного case.

**Проверка.** `tools/run_stage0_baseline.ps1` создаёт по одному artifact-каталогу на testcase и завершает только принадлежащий ему дочерний процесс при timeout.

**Последствия.** Для CI понадобится явно установить ту же версию SDK или осознанно обновить baseline после миграции.

## D-006. Для Ren'Py exception авторитетен свежий traceback, а не exit code

**Дата:** 2026-10-17
**Статус:** реализовано в runner

**Контекст.** В Ren'Py 8.3.4 команда `test` возвращает exit code `0` даже после uncaught game exception, показанного на error screen.

**Решение.** Expected-exception сценарий сопоставляется по свежему `traceback.txt`, созданному не раньше старта конкретного процесса, и точной regex-сигнатуре. Для обычного успешного сценария любой свежий `traceback.txt` или `errors.txt` запрещает `PASS`, даже при exit code `0`. Каталог конкретного case очищается перед запуском. Exit code сохраняется как наблюдение, но не используется как единственное доказательство.

**Альтернативы.** Требовать nonzero; искать текст в общем старом логе; считать любое появление traceback успешным совпадением.

**Компромиссы.** Сигнатуры нужно поддерживать при изменении текста ошибок. Проверка времени файла и отдельный artifact-каталог уменьшают риск ложного совпадения со старой ошибкой.

**Проверка.** Оба известных crash-сценария вернули `0`, но свежие traceback содержали соответственно `ATLTransform ... __init__ ... atl` и `MultipleTransition ... not callable`.

**Последствия.** После исправления handlers эти сценарии должны ожидать нормальное завершение и отсутствие traceback.

## D-007. GUI можно проектировать параллельно, но динамические экраны зависят от state model

**Дата:** 2026-10-16
**Статус:** принято в плане

**Контекст.** Замена дефолтного Ren'Py GUI в основном состоит из screens, styles и графических assets, но History, Save/Load, ожидание генерации и error overlay отображают динамическое состояние.

**Решение.** Визуальные концепты и дизайн-систему можно готовить параллельно. Подключение динамических данных выполнять после стабилизации `PlaybackState` и формата save metadata; стандартные Ren'Py Actions сохранять.

**Альтернативы.** Полностью отложить GUI; сначала заменить все картинки и одновременно переписать логику экранов.

**Компромиссы.** Параллельная работа ускоряет подготовку assets, но ранние динамические макеты могут потребовать адаптации после утверждения state model.

**Проверка.** Stage 0 визуально подтвердил, что default History получает три динамические реплики; проблема находится не только в оформлении, а в жизненном цикле player/save/rollback.

**Последствия.** Не запекать текст в изображения; предусмотреть состояния loading/error/disabled и кириллицу; масштабируемые панели делать через `Frame`/9-slice.

## D-008. Контракт сцены v1 строгий, ограниченный и fail-closed

**Дата:** 2026-10-17
**Статус:** реализовано локально

**Контекст.** JSON приходит от будущей LLM и потому является недоверенным вводом. Старый player молча пропускал неизвестные действия и отсутствующие ресурсы; генератор и handlers описывали разные форматы.

**Решение.** Ввести обязательные `schema_version: 1`, `scene_id`, `characters` и `dialogue`; запрещать неизвестные поля/actions, дубли JSON-ключей, неподдерживаемые версии и несуществующие изображения до вызова handlers. Ограничить сырой файл 1 MiB, глубину 20, число узлов 10 000, действия 500 и размеры строк. `music` исключить из v1 до появления handler и реальных ресурсов.

**Альтернативы.** Сохранять permissive parsing; игнорировать незнакомые действия; принимать JSON Schema только как документацию; сразу добавить фиктивный `music` handler.

**Компромиссы.** Строгий формат хуже переносит произвольный LLM-вывод и требует явной миграции, зато ошибка наблюдаема и не превращается в частично проигранную сцену. Python и Ren'Py пока содержат два валидатора, поэтому добавлены parity/invariant-тесты, но риск рассинхронизации остаётся.

**Проверка.** Native tests покрывают malformed/scalar/deep/oversized JSON, duplicate keys, версии, неизвестные actions, отсутствующие images, запрет запуска handlers и удаление отвергнутой задачи из локальной очереди. Python boundary suite проверяет те же числовые и структурные границы, итоговый UTF-8 размер и запрет non-finite JSON. Итог: Ren'Py `29/29`, Python `20/20`.

**Последствия.** Любое расширение v1 требует одной поставкой обновить Schema, оба валидатора, handler registry, ресурсы и тесты. Для v2 понадобится явная миграция, а не неявное принятие новых полей.

## D-009. Save хранит проверенный snapshot, а не ссылку на внешний файл

**Дата:** 2026-10-17
**Статус:** реализовано локально

**Контекст.** Файл сцены и MongoDB могут измениться или исчезнуть после сохранения. Повторное чтение внешнего источника при load делает сохранение недетерминированным.

**Решение.** После нормализации хранить в `PlaybackState` глубокую копию JSON-safe snapshot, `scene_id`, версию схемы, канонический SHA-256, `step_index`, переменные/trace ветвления, фазу и структурированную ошибку. При восстановлении проверять целостность snapshot; не перечитывать сцену из MongoDB или файла.

**Альтернативы.** Хранить только путь и индекс; перечитывать актуальный JSON; сериализовать runtime-объекты handlers/Character.

**Компромиссы.** Save становится больше и требует версии state, зато воспроизведение не зависит от очереди и внешнего файла. Player функционально заменяет state после каждого успешного действия; cursor всегда указывает на текущее незавершённое действие.

**Проверка.** Native save/load roundtrip восстанавливает state и hash; tampering-тесты отклоняют неверный hash, cursor, phase и не-JSON-safe значения.

**Последствия.** Каждое действие выполняется в физической Ren'Py script boundary; изменение порядка handler и cursor commit требует отдельной save/load/rollback-регрессии.

## D-011. Одно JSON-действие соответствует одной итерации Ren'Py label-loop

**Дата:** 2026-10-18
**Статус:** реализовано локально

**Контекст.** Python frame внутри одного длинного вызова не сериализуется как продолжение выполнения. Save во время `renpy.say` восстанавливает начало текущего statement, поэтому cursor должен описывать незавершённое, а не уже показанное действие.

**Решение.** Подготовка сцены и исполнение разделены. Label-loop вызывает ровно один handler, затем отдельным Ren'Py statement функционально заменяет `PlaybackState` и сдвигает cursor. Handlers возвращают явный `PlaybackActionResult`; `jump` становится `goto`, а фактический переход выполняет вызывающий label.

**Компромиссы.** У цикла больше script boundaries и служебных объектов. Взамен save/load и rollback используют штатный журнал Ren'Py, а handler error оставляет точный cursor и snapshot.

**Проверка.** Native cases покрывают cursor progression, save/load `1/2/2`, rollback 1/3/10 и границу сцен, `return`, natural end, `goto` с branch trace, handler/middleware error и hard checkpoint `pause`.

## D-012. History и save metadata используют поддерживаемые callbacks Ren'Py

**Дата:** 2026-10-18
**Статус:** реализовано локально

**Контекст.** Ручное добавление и замена элементов приватного `_history_list` дублировали штатную запись `renpy.say` и ломали связь с rollback log.

**Решение.** На каждую реплику вызывается один `renpy.say`. `config.history_callbacks` только аннотирует штатный `HistoryEntry` полями `scene_id`, `step_index`, `speaker_id`; экран History использует сохранённый `rollback_identifier` через `RollbackToIdentifier`. `config.save_json_callbacks` добавляет инертный блок `ai_novel` для UI слотов, но gameplay state остаётся обычным store state.

**Компромиссы.** Метаданные зависят от поддерживаемых callback API конкретной версии Ren'Py. Slot JSON пригоден для отображения и диагностики, но не является источником восстановления.

**Проверка.** Native cases проверяют отсутствие дублей после load, аннотации всех реплик, чувствительность и реальный UI-переход History, точный slot JSON и отсутствие metadata для недоверенного state.

## D-013. Клиент подтверждает потребление, но не удаляет внешнюю задачу

**Дата:** 2026-10-18
**Статус:** реализовано локально

**Контекст.** MongoDB не откатывается вместе с Ren'Py. `delete_one` внутри клиентского control flow мог необратимо уничтожить задачу при повторном входе после load/rollback.

**Решение.** `consume_task` сначала требует подтверждённое условное обновление `{status: done} → {status: consumed}` либо уже сохранённый `consumed`. При exception или другом статусе локальная очередь не меняется, а label повторяет только ack. После успеха successor-задача создаётся с детерминированным `_id`, вычисленным из queue-session и предыдущей задачи, поэтому восстановление до ack не создаёт вторую ветку. При загрузке старого локального состояния refill проходит уже терминальные `consumed/error` successors и продолжает ту же детерминированную цепочку. Очистка и retention переданы внешнему сервису.

**Компромиссы.** В Mongo накапливается история задач и понадобится отдельная retention policy. За один refill просмотр ограничен 1000 терминальными звеньями: это защищает UI от бесконечного обхода, но очень старой очереди потребуется серверная очистка или курсор восстановления. Зато rollbackable-клиент не владеет необратимым удалением внешних данных.

**Проверка.** Regression вызывает `consume_task` дважды после восстановления локальной очереди, запрещает `delete_one`, подтверждает одно Mongo-обновление и один уникальный successor key. Отдельный сценарий проходит цепочку `consumed → error → fresh` и набирает три новые задачи. При exception и неожиданном status исходная задача остаётся локально для retry.

## D-014. Несовместимые версии PlaybackState отклоняются fail-closed

**Дата:** 2026-10-18
**Статус:** принято и реализовано локально

**Контекст.** `PlaybackState` v1 создавался до появления пошаговых фаз и точного cursor commit. Автоматически угадать безопасную позицию продолжения невозможно.

**Решение.** Текущая версия state — 2. `after_load` и защита непосредственно перед handler проверяют версию, hash, phase и cursor. Любое несовместимое или повреждённое состояние заменяется структурированной ошибкой до выполнения действия; неявной миграции v1 → v2 нет.

**Альтернатива.** Поддерживать эвристику миграции или молча начинать сцену заново.

**Компромиссы.** Старые тестовые сохранения становятся несовместимыми. Это честнее и безопаснее, чем повторять уже показанные действия или внешние эффекты; будущая миграция потребует отдельного доказуемого преобразования.

**Проверка.** Native integrity case подменяет `state_version`, проверяет отказ и отсутствие вызова handler; отдельный настоящий `FileLoad` проходит callbacks/`after_load`, показывает отказ и уходит в главное меню, не возобновляя сохранённый statement. Валидный v2 state проходит save/load roundtrip.

## D-015. Недоверенный JSON не получает произвольный Ren'Py control flow

**Дата:** 2026-10-18
**Статус:** реализовано локально

**Контекст.** Проверки существования label недостаточно: AI мог выбрать внутренний или тестовый label. Кроме того, Ren'Py интерпретирует `[...]`, text tags и hyperlink tags внутри строк диалога.

**Решение.** Production `jump` ограничен явным allowlist (`next_scene`), одинаковым в клиенте, JSON Schema и Python-валидаторе. Test labels добавляются только при команде native tests. Перед созданием `Character` и `renpy.say` недоверенные имена и реплики экранируют `[`, `{` и `【`, поэтому интерполяция, text tags, ruby и hyperlink actions отображаются буквально.

**Компромиссы.** v1 не разрешает авторское форматирование текста из AI. Безопасные теги можно добавить позже только явным whitelist и отдельной версией контракта.

**Проверка.** Native fixtures отклоняют переход в `start` до handler и дословно воспроизводят строку с interpolation/hyperlink/ruby markers без перехода или чтения store. Python parity test принимает только `next_scene`.

## D-016. Фаза `playing` всегда указывает на существующее действие

**Дата:** 2026-10-18
**Статус:** реализовано локально

**Контекст.** Проверка сохранённого state обязана отвергать `playing` с cursor за концом `dialogue`. Первоначальная state machine после последнего обычного `continue` кратковременно создавала именно такое состояние и рассчитывала завершить его на следующей итерации label-loop. После усиления integrity-проверки natural end стал корректно отклоняться как повреждённый state.

**Решение.** `PlaybackState.after_success` вычисляет следующий cursor и атомарно переводит state в `completed`, если успешное действие было последним. Явные `return` и `goto` остаются терминальными независимо от оставшегося хвоста; промежуточной фазы `playing` без текущего действия больше нет.

**Компромиссы.** Логика завершения находится в state transition, а не в следующем проходе label-loop. Это немного связывает переход с длиной snapshot, но делает каждый сериализуемый state самодостаточным и проверяемым после save/load.

**Проверка.** Отдельно проходят natural end, явный `return`, `goto`, cursor progression и integrity tampering. Финальная матрица Этапов 0–3: JSON `36/36`, lint `PASS`, native cases `53/53`, `overall_passed=true`; Python-оркестратор — `20/20` unit tests.

## D-010. Публикация сцены атомарна, а task id является её идентичностью

**Дата:** 2026-10-17
**Статус:** реализовано локально

**Контекст.** Клиент ожидает `scene_<task_id>.json` и проверяет `scene_id == task_id`. Прежний demo-generator выдавал постоянный id, а worker мог поставить `done` после отсутствующего результата или ошибки записи.

**Решение.** Передавать task id в генератор как `scene_id`. До публикации проверять контракт и совпадение id, один раз сериализовать JSON с запретом `NaN/Infinity`, проверить фактический UTF-8 размер до 1 MiB, затем записать именно эти байты во временный файл, выполнить flush/fsync, `os.replace`, перечитать и повторно проверить JSON. Только после этого ставить `done`; иначе сохранять структурированную ошибку. Если клиент всё же отклонил `done`-сцену, он переводит задачу в `error`, удаляет её из локальной очереди и продолжает со следующей.

**Альтернативы.** Записывать прямо в итоговый файл; считать успешным сам вызов `json.dump`; хранить произвольный scene id; оставлять задачу в `done` с путём на отсутствующий файл.

**Компромиссы.** Локальный Python-валидатор дублирует часть клиентского контракта, а `fsync` добавляет небольшую задержку. Взамен клиент не видит частично записанный файл и получает стабильную связь задача–файл–snapshot.

**Проверка.** Unit tests покрывают `None`, malformed contract, mismatch id, `NaN/Infinity`, файл больше 1 MiB, отказ `os.replace` и happy path без оставшегося `.tmp`; native queue tests подтверждают `ready → play → consume` ровно один раз и `invalid → reject → next` без повторного выбора ошибочной задачи.

**Последствия.** При подключении AI Gateway он обязан выдавать тот же v1 и не может переводить задачу в `generated/done` в обход этой границы.

## D-017. SceneProvider отделяет rollbackable state от внешнего I/O

**Дата:** 2026-10-19
**Статус:** реализовано локально

**Контекст.** Клиент напрямую смешивал MongoDB polling, выбор файла, проигрывание и удаление задачи внутри rollbackable control flow. Недоступная база оставляла интерфейс ждать длинный driver timeout, повторный вход мог переиграть сцену, а autosave мог попасть между окончанием playback и внешним подтверждением.

**Решение.** Ввести границу `SceneProvider` с реализациями для task/file, Mongo-adapter и fixtures. В save хранится только версионированный JSON-safe `SceneSessionState`; live provider находится в `renpy.session` и пересоздаётся после load. Poll/prepare/playback/acknowledge возвращают структурированный результат или `SceneProviderError`, а UI предлагает Retry/Main Menu. MongoDB получает короткие timeouts, один poll имеет ограниченный бюджет remote-операций и сохраняемый cursor обхода. Сцена сначала завершается, затем идемпотентно подтверждается как `consumed`, после чего отдельный Ren'Py statement фиксирует `boundary` и выполняет блокирующий autosave.

**Альтернативы.** Оставить прямой вызов очереди из script labels; считать любой timeout отсутствующей задачей; повторять всю сцену после ошибки; запускать неблокирующий autosave сразу после playback; сохранить MongoClient/provider внутри store.

**Компромиссы.** Текущие MongoDB-вызовы остаются синхронными на interaction thread. Короткие timeouts и bounded work делают паузу ограниченной и наблюдаемой, но не заменяют production API/local adapter или асинхронную доставку. Retry playback намеренно разрешён только для `return`/`jump`: после ошибки реплики или визуального действия нельзя доказать отсутствие частичного эффекта. Обычные interaction autosave отключены для динамической сцены, чтобы не сохранять неустойчивую точку между playback и ack.

**Проверка.** Native cases проверяют provider contract, ordered task errors, bounded polling и продолжение traversal, offline UI менее чем за 8 секунд, Retry/Main Menu, ack retry без повтора сцены, безопасный playback retry с сохранением cursor, настоящий blocking autosave и последующий load `boundary`, а также fail-closed загрузку повреждённой session. Финальная матрица: JSON `37/37`, lint `PASS`, native cases `62/62`, `overall_passed=true`, свежих error diagnostics нет. Python-оркестратор: `20/20`.

**Последствия.** Этап 4 закрывает локальную клиентскую границу ошибок, но не доказывает реальный MongoDB/Compose end-to-end. Следующий клиентский этап — кастомный GUI; отдельно нужны worker recovery/lease и перенос provider I/O с interaction thread.
